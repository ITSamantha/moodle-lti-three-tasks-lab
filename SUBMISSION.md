Репозиторий (без `node_modules`, `.env`, `data`, ключей; `.env.example` приложен):
https://github.com/ITSamantha/moodle-lti-three-tasks-lab

## 2. Описание вопросов

Тема: **веб-технологии (HTML/CSS)**. Файл: `src/grading.mjs`.

| id | Формулировка | Допустимый ответ | Вес |
|----|---|---|---|
| q1 | Какой тег HTML задаёт самый крупный заголовок страницы? | `h1` | 3 |
| q2 | Какое CSS-свойство задаёт цвет текста? | `color` | 3 |
| q3 | Каким свойством в CSS центрируют flex-контейнер по главной оси? | `justify-content` | 4 |

Сумма весов: 3 + 3 + 4 = **10**.

**Нормализация**: перед сравнением ответ приводится к нижнему регистру, пробелы по краям
убираются (`normalize()` в `src/grading.mjs`). Регистр и лишние пробелы не влияют на оценку —
проверено тестом `case and whitespace insensitive answers for own questions`.

**Пустой и некорректный ответ**:
- Если передано не ровно три ключа `q1`/`q2`/`q3` — сервер отвечает HTTP 400, оценка не
  вычисляется и не отправляется в Moodle.
- Если значение ответа не строка или длиннее 200 символов — HTTP 400, без отправки оценки.
- Пустая строка (`''`) как ответ — допустимое значение по форме, но после нормализации она не
  совпадает ни с одним правильным ответом, поэтому балл за такой вопрос — 0 (проверено тестом
  `normalization and zero score`).

## 4. Тесты

```
$ npm test

✔ normalization and zero score
✔ maximum and partial result
✔ invalid answers cannot become grades
✔ case and whitespace insensitive answers for own questions
✔ signed LTI launch, AGS, isolation, replay and failure recovery

tests 5, pass 5, fail 0
```

Строка `AGS не подтвердил оценку: HttpError` в выводе — ожидаемая часть интеграционного теста
(он намеренно имитирует сбой AGS-сервиса, чтобы проверить, что попытка сохраняется и
интерфейс предлагает повтор).

Собственный добавленный тест (`case and whitespace insensitive answers for own questions` в
`test/grading.test.mjs`): проверяет, что ответы с пробелами по краям и в произвольном регистре
(`'  H1  '`, `'COLOR'`, `'Justify-Content'`) засчитываются как верные и дают максимум 10/10.

**Что проверено на настоящем Moodle, а что на имитации:**
- На имитации (`npm test`, встроенный тест-раннер Node, без реального Moodle/MongoDB):
  расчёт оценки, подписанный LTI-запуск, разделение студентов, запрет роли Instructor,
  подмена userId, повтор nonce, восстановление после сбоя AGS.
- На настоящем Moodle (gnomio, вручную через UI и тестовые аккаунты): полный цикл запуска из
  элемента курса, отображение формы, отправка ответов, подтверждение AGS, попадание оценки в
  журнал у двух разных студентов, разница результатов по правилу «последняя завершённая
  попытка».

## 5. Краткий разбор

**Поток «запуск → ответы → расчёт → AGS → журнал»:**
1. Студент открывает элемент курса → Moodle делает подписанный LTI 1.3 launch на
   `/lti/launch`. Библиотека `ltijs` проверяет подпись и создаёт контекст (`provider.onResourceLink`
   в `src/tool.mjs`).
2. Сервер создаёт одноразовый билет (`ticket`) и редиректит на `/app/start?ticket=...`, который
   превращает билет в сессию интерфейса (cookie `__Host-lti_lab`, 45 минут жизни).
3. Браузер получает список заданий через `GET /api/session` (без правильных ответов — они не
   покидают сервер) и собирает ответы в форме.
4. `POST /api/submit` с `answers` и `requestId`: сервер выполняет серверный расчёт `grade()`,
   сохраняет попытку, затем вызывает `context.grading.submitScore(ags.lineItemId, ...)` —
   это и есть вызов AGS с `userId` из проверенного токена, а не из тела запроса браузера.
5. При успехе Moodle подтверждает приём, попытка помечается `sent`, появляется кнопка «Новая
   попытка». Журнал Moodle обновляет строку `line item` для этого студента.

**Повторная отправка vs новая попытка:** пока текущая попытка не подтверждена Moodle
(`sentAt == null`), повторная отправка того же `requestId`/набора ответов не создаёт новую
запись — сервер переиспользует уже посчитанный результат и просто повторяет вызов AGS. Новая
попытка (кнопка «Новая попытка», доступна только после подтверждения) переносит текущую
попытку в историю и обнуляет `current`, разрешая новый расчёт.

**Демонстрация изменения правила** (для индивидуальной защиты): изменить вес вопроса q1 с 3 на
2 и вопроса q3 с 4 на 5 в `src/grading.mjs` (сумма остаётся 10), перезапустить тесты — тест
`maximum and partial result` по-прежнему проходит (он читает веса динамически из массива
`tasks`), затем показать, что при верном q1 и неверных остальных итоговый балл меняется с 3 на 2.
